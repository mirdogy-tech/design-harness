## 1. design-ops (프로덕트 디자인 팀 오케스트레이터)

**핵심 역할**: 여러 디자인 단계를 아우르는 복합 요청을 팀 단위로 오케스트레이션. 리서치 > 디자인 > 구현의 파이프라인을 조율한다.

### Should-trigger (트리거되어야 하는 쿼리)

| # | 쿼리 | 트리거 근거 |
|---|------|-----------|
| 1 | "신규 온보딩 화면을 설계해줘. 경쟁사 조사부터 컴포넌트 구현까지 전부." | 리서치 > 디자인 > 구현 전체 프로세스 |
| 2 | "디자인 팀 구성해서 결제 플로우 개선 프로젝트 시작해줘" | '디자인 팀' 명시적 언급 |
| 3 | "리서치부터 구현까지 전체 디자인 프로세스로 진행해줘" | '리서치부터 구현까지', '전체 디자인 프로세스' 키워드 |
| 4 | "사용자 조사 결과를 반영해서 화면 설계하고 코드까지 뽑아줘" | 3단계(조사 > 설계 > 코드)에 걸친 복합 요청 |
| 5 | "이 기능에 대해 UX 리서치도 하고 와이어프레임도 만들어줘" | 2개 이상 전문 영역(리서치 + 디자인) 동시 요청 |
| 6 | "디자인 프로젝트를 시작하려는데, 경쟁사 분석과 UI 설계를 같이 진행해줘" | '디자인 프로젝트' + 복합 단계 |
| 7 | "프로필 페이지를 처음부터 끝까지 만들어줘 — 사용자 리서치부터" | 암시적 전체 프로세스 요청 |
| 8 | "팀으로 일해서 검색 기능 UX를 개선해줘" | '팀으로 일해서' = 팀 협업 요청 |
| 9 | "알림 시스템 디자인해줘. 벤치마크 조사하고 와이어프레임 잡고 React 컴포넌트까지" | 3단계 파이프라인 명시 |
| 10 | "디자인팀 돌려서 대시보드 전면 리디자인 해줘" | '디자인팀 돌려서' = 팀 오케스트레이션 |

### Should-NOT-trigger (트리거되지 않아야 하는 쿼리)

| # | 쿼리 | 적합한 스킬 | near-miss 근거 |
|---|------|-----------|---------------|
| 1 | "온보딩 화면 와이어프레임만 빠르게 그려줘" | ui-design | '화면 설계'지만 단일 작업, 팀 협업 불필요 |
| 2 | "경쟁사 온보딩 벤치마크 보고서 작성해줘" | deep-research | '경쟁사 분석'이지만 리서치 단독 작업 |
| 3 | "이 A/B 테스트 결과 분석해줘" | ux-research | 디자인 관련이지만 리서치 단독 |
| 4 | "버튼 컴포넌트 코드 만들어줘" | ui-build | 구현 단독 작업 |
| 5 | "사용자 인터뷰 데이터에서 페르소나 뽑아줘" | ux-research | 디자인 프로세스 일부지만 리서치 단독 |
| 6 | "Figma 파일 보고 코드로 옮겨줘" | ui-build | 디자인 > 코드이지만 단순 변환, 오케스트레이션 불필요 |
| 7 | "컬러 팔레트 새로 잡아줘" | ui-design | 비주얼 디자인이지만 단일 작업 |
| 8 | "시장 조사 보고서 써줘 — SaaS 결제 트렌드" | deep-research | '조사 보고서'이지만 디자인 무관 리서치 |
| 9 | "디자인 토큰을 CSS 변수로 변환해줘" | ui-build | 디자인 시스템 관련이지만 코드 구현 단독 |

## 2. ux-research (UX 리서치 & A/B 테스트)

**핵심 역할**: 사용자 조사(인터뷰 분석, 페르소나, 여정 맵, 사용성 평가)와 A/B 테스트(설계, 통계 분석, 결과 해석).

### Should-trigger (트리거되어야 하는 쿼리)

| # | 쿼리 | 트리거 근거 |
|---|------|-----------|
| 1 | "사용자 인터뷰 5건의 데이터를 분석해서 인사이트 뽑아줘" | 인터뷰 분석 |
| 2 | "우리 앱 사용자 페르소나 3개 만들어줘" | 페르소나 생성 |
| 3 | "구매 플로우의 사용자 여정 맵을 그려줘" | 여정 맵 |
| 4 | "이 두 버전의 A/B 테스트 결과를 분석해줘. p-value 포함해서" | A/B 테스트 통계 분석 |
| 5 | "checkout 페이지 사용성 테스트 시나리오 설계해줘" | 사용성 테스트 |
| 6 | "전환율이 떨어지는 원인을 유저 리서치로 파악해줘" | 전환율 + 유저 리서치 |
| 7 | "두 변형안 비교 분석 부탁해" | '변형안 비교' |
| 8 | "CTA 버튼 색상 변경이 전환율에 미치는 영향 테스트 설계해줘" | A/B 테스트 설계 |
| 9 | "usability evaluation of our search feature" | 'usability' 키워드 |
| 10 | "이 기능에 대한 사용자 조사를 진행하려고 하는데 리서치 계획을 세워줘" | '사용자 조사' + 리서치 계획 |

### Should-NOT-trigger (트리거되지 않아야 하는 쿼리)

| # | 쿼리 | 적합한 스킬 | near-miss 근거 |
|---|------|-----------|---------------|
| 1 | "경쟁사 제품의 사용자 후기 분석해줘" | deep-research | '사용자' 포함이지만 자사 UX 리서치가 아닌 경쟁사 외부 데이터 수집 |
| 2 | "SaaS 시장에서 어떤 UX 트렌드가 있는지 조사해줘" | deep-research | 'UX'가 포함되지만 시장/트렌드 조사 = 딥 리서치 |
| 3 | "사용자 플로우를 설계해줘" | ui-design | '사용자'가 포함되지만 UX 플로우 설계 = UI 설계 |
| 4 | "전환율 높이려면 버튼을 어디에 배치해야 할까?" | ui-design | '전환율'이 나오지만 실제 요청은 레이아웃 설계 |
| 5 | "Reddit에서 우리 앱에 대한 사용자 반응 수집해줘" | deep-research | '사용자 반응'이지만 커뮤니티 크롤링 = 딥 리서치 |
| 6 | "이 인터뷰 결과를 바탕으로 와이어프레임 만들어줘" | ui-design (또는 design-ops) | '인터뷰 결과'가 있지만 핵심 요청은 와이어프레임 |
| 7 | "사용자가 쓰기 편한 폼 컴포넌트 만들어줘" | ui-build | '사용자'+'쓰기 편한'이지만 핵심은 컴포넌트 구현 |
| 8 | "회원가입 퍼널 데이터 시각화해줘" | (일반 작업) | '퍼널'+'전환'이 UX 연상이지만 데이터 시각화는 리서치가 아님 |
| 9 | "사용자 경험 향상을 위한 디자인 가이드라인 만들어줘" | ui-design | 'UX 향상'이지만 산출물이 디자인 시스템/가이드라인 |

## 3. deep-research (딥 리서치)

**핵심 역할**: 웹, 학술, 커뮤니티 등 다중 소스를 교차 검증하여 종합 보고서 작성. 단순 검색이 아닌 심층 조사.

### Should-trigger (트리거되어야 하는 쿼리)

| # | 쿼리 | 트리거 근거 |
|---|------|-----------|
| 1 | "모바일 결제 UX 트렌드에 대해 딥 리서치 해줘" | '딥 리서치' 명시 |
| 2 | "경쟁사 분석 보고서 작성해줘 — Notion, Coda, Slite 비교" | '경쟁사 분석' |
| 3 | "다크 모드가 사용성에 미치는 영향에 대해 학술 논문 찾아서 정리해줘" | '학술 논문' + '조사' |
| 4 | "최근 SaaS 대시보드 디자인 벤치마크 조사해줘" | '벤치마크' |
| 5 | "Product Hunt에서 올해 인기 있는 디자인 툴 반응 분석해줘" | 커뮤니티 반응 분석 |
| 6 | "AI 기반 코드 에디터 시장 현황 심층 조사해줘" | '심층 조사', '시장 조사' |
| 7 | "이 기능에 대한 Reddit, HN 반응을 수집하고 감성 분석해줘" | '커뮤니티 반응' + '소셜 분석' |
| 8 | "음성 인터페이스 기술 동향 보고서 써줘" | '기술 동향' |
| 9 | "deep research on progressive disclosure patterns in complex forms" | 'deep research' 영문 |
| 10 | "여러 출처에서 교차 검증해서 리서치 보고서 만들어줘" | '교차 검증' + '리서치 보고서' |

### Should-NOT-trigger (트리거되지 않아야 하는 쿼리)

| # | 쿼리 | 적합한 스킬 | near-miss 근거 |
|---|------|-----------|---------------|
| 1 | "사용자 인터뷰 결과를 분석해서 인사이트 뽑아줘" | ux-research | '분석'이 나오지만 1차 데이터(인터뷰) 분석 = UX 리서치 |
| 2 | "우리 제품 사용자 여정을 조사해줘" | ux-research | '조사'가 있지만 자사 사용자 대상 = UX 리서치 |
| 3 | "A/B 테스트 결과의 통계적 유의성 검증해줘" | ux-research | '검증'이 포함되지만 A/B 테스트 = UX 리서치 |
| 4 | "경쟁사 앱의 네비게이션 구조를 분석해서 와이어프레임에 반영해줘" | design-ops | '경쟁사 분석'이지만 최종 목표가 와이어프레임 = 복합 작업 |
| 5 | "이 논문 내용 요약해줘" | (일반 작업) | '논문'이 연상이지만 단순 요약은 딥 리서치 수준 아님 |
| 6 | "검색 기능 관련 기술 스택 조사해줘" | (일반 작업/엔지니어링) | '기술 조사'이지만 구현 관련 기술 선택 = 개발 영역 |
| 7 | "이 트렌드 조사 결과 바탕으로 디자인 시스템 만들어줘" | design-ops | '트렌드 조사'가 있지만 핵심 요청은 디자인 시스템 구축 |
| 8 | "우리 앱 사용 데이터 로그 분석해줘" | ux-research | '데이터 분석'이지만 자사 로그 = 정량적 UX 리서치 |
| 9 | "Figma 커뮤니티에서 인기 있는 UI Kit 찾아줘" | ui-design | '커뮤니티'가 있지만 디자인 리소스 탐색 = UI 설계 영역 |

## 4. ui-design (UI 설계 & 디자인)

**핵심 역할**: 와이어프레임, UX 플로우, 정보 구조(IA), 비주얼 디자인, 디자인 토큰 정의. Figma 연동.

### Should-trigger (트리거되어야 하는 쿼리)

| # | 쿼리 | 트리거 근거 |
|---|------|-----------|
| 1 | "로그인 화면 와이어프레임 그려줘" | '와이어프레임' |
| 2 | "이 기능의 UX 플로우를 설계해줘" | 'UX 플로우' |
| 3 | "앱의 정보 구조(IA)를 잡아줘" | '정보 구조', 'IA' |
| 4 | "우리 서비스 컬러 팔레트를 새로 정의해줘" | '컬러 팔레트' |
| 5 | "디자인 토큰을 정의해줘 — 색상, 타이포, 스페이싱" | '디자인 토큰' 정의 (구현 아님) |

| 7 | "모바일 네비게이션 구조를 설계해줘" | '네비게이션 설계' |
| 8 | "설정 화면 목업 만들어줘" | '목업' |

| 10 | "타이포그래피 스케일 잡아줘" | '타이포그래피' |

### Should-NOT-trigger (트리거되지 않아야 하는 쿼리)

| # | 쿼리 | 적합한 스킬 | near-miss 근거 |
|---|------|-----------|---------------|
| 1 | "디자인 토큰을 CSS 변수로 구현해줘" | ui-build | '디자인 토큰'이지만 '구현/코드 변환' = ui-build |
| 2 | "이 와이어프레임 기반으로 React 컴포넌트 만들어줘" | ui-build | '와이어프레임'이 나오지만 핵심은 코드 생성 |
| 3 | "Figma 디자인을 코드로 변환해줘" | ui-build | 'Figma'가 있지만 Figma-to-Code = ui-build |
| 4 | "이 화면에서 사용자가 왜 이탈하는지 알아봐줘" | ux-research | '화면' 언급이지만 이탈 원인 = 사용자 조사 |
| 5 | "UI 디자인 트렌드를 조사해줘" | deep-research | 'UI 디자인'이 있지만 '트렌드 조사' = 딥 리서치 |
| 6 | "디자인 시스템 코드를 Storybook으로 만들어줘" | ui-build | '디자인 시스템'이 있지만 Storybook 코드 구현 = ui-build |
| 7 | "화면 설계하고 컴포넌트까지 만들어줘" | design-ops | '화면 설계'가 있지만 복합 요청(설계 + 구현) = 오케스트레이터 |
| 8 | "경쟁사 앱 UI를 벤치마크해줘" | deep-research | 'UI'가 있지만 '벤치마크' = 딥 리서치 |
| 9 | "이 레이아웃의 접근성을 평가해줘" | ux-research | '레이아웃'이지만 '평가' = 사용성 평가 영역 |

## 5. ui-build (UI 컴포넌트 빌드)

**핵심 역할**: 디자인 명세를 실제 코드(React, Vue, HTML/CSS)로 변환. 디자인 토큰 구현, 컴포넌트 라이브러리, Figma-to-Code.

### Should-trigger (트리거되어야 하는 쿼리)

| # | 쿼리 | 트리거 근거 |
|---|------|-----------|
| 1 | "이 디자인 명세서 보고 React 컴포넌트 만들어줘" | 디자인 명세 > 코드 |
| 2 | "버튼 컴포넌트를 primary, secondary, ghost 변형으로 만들어줘" | '버튼 컴포넌트' |
| 3 | "디자인 토큰을 Tailwind config로 구현해줘" | '디자인 토큰 구현' |
| 4 | "이 Figma 디자인을 코드로 변환해줘" | 'Figma to Code' |
| 5 | "카드 컴포넌트에 반응형 레이아웃 적용해서 만들어줘" | '카드 컴포넌트' + 코드 |
| 6 | "Storybook에 컴포넌트 스토리 추가해줘" | 'Storybook' |
| 7 | "디자인 시스템 코드 라이브러리 구축해줘" | '디자인 시스템 코드', '컴포넌트 라이브러리' |
| 8 | "이 목업을 HTML/CSS로 코딩해줘" | 디자인 > HTML/CSS 코드 변환 |
| 9 | "모달 컴포넌트 코드 짜줘, 접근성 포함해서" | '컴포넌트 코드' |
| 10 | "CSS 변수 기반으로 테마 시스템 구현해줘" | 'CSS 구현' + 디자인 토큰 |

### Should-NOT-trigger (트리거되지 않아야 하는 쿼리)

| # | 쿼리 | 적합한 스킬 | near-miss 근거 |
|---|------|-----------|---------------|
| 1 | "버튼 컴포넌트의 디자인 명세를 작성해줘" | ui-design | '버튼 컴포넌트'이지만 '명세 작성' = 설계 |
| 2 | "디자인 토큰(색상, 스페이싱)을 정의해줘" | ui-design | '디자인 토큰'이지만 '정의' vs '구현'의 차이 |
| 3 | "카드 컴포넌트 레이아웃을 설계해줘" | ui-design | '카드 컴포넌트'이지만 '설계' = 와이어프레임 |
| 4 | "컴포넌트 라이브러리를 어떻게 구성할지 벤치마크 조사해줘" | deep-research | '컴포넌트 라이브러리'이지만 '벤치마크 조사' = 딥 리서치 |
| 5 | "이 컴포넌트의 사용성을 테스트해줘" | ux-research | '컴포넌트'이지만 '사용성 테스트' = UX 리서치 |
| 6 | "Figma에서 디자인 시스템 변수 확인해줘" | ui-design | 'Figma', '디자인 시스템'이지만 분석/확인 = 설계 영역 |
| 7 | "컴포넌트 설계 후 코드까지 만들어줘" | design-ops | '코드'가 있지만 '설계 + 코드' 복합 요청 = 오케스트레이터 |
| 8 | "이 UI의 접근성 개선 방안을 제안해줘" | ui-design (또는 ux-research) | 'UI'+'접근성'이지만 개선 '제안' = 설계/평가 영역 |
| 9 | "REST API 엔드포인트 코드 만들어줘" | (일반 개발) | '코드 만들어줘'이지만 UI 컴포넌트가 아닌 백엔드 |

## 6. 트리거 충돌 분석

5개 스킬 간 동일 쿼리에 2개 이상이 트리거될 수 있는 경계 영역을 분석한다.

### 충돌 패턴 A: ux-research vs deep-research

| 충돌 쿼리 | ux-research 근거 | deep-research 근거 | 판정 |
|----------|-----------------|-------------------|------|
| "사용자 반응을 조사해줘" | '사용자 조사' 키워드 매칭 | '커뮤니티 반응' 수집 가능 | **의도에 따라 다름** — 자사 사용자 1차 데이터면 ux-research, 외부 커뮤니티 2차 데이터면 deep-research. 모호하므로 명확화 필요. |
| "UX 트렌드 리서치 해줘" | 'UX 리서치' 키워드 매칭 | '트렌드 분석' 키워드 매칭 | **deep-research가 적합** — '트렌드'가 핵심 의도. 그러나 'UX 리서치'가 ux-research를 트리거할 가능성 높음. 충돌 위험. |
| "전환율 데이터를 분석해줘" | '전환율 분석' 키워드 매칭 | 시장 데이터 분석으로도 해석 가능 | **ux-research가 적합** — 자사 데이터 분석이 기본 의도. 충돌 가능성 낮음. |

**심각도**: 중간. '리서치'라는 단어가 두 스킬 모두에 핵심 키워드로 들어가 있어 구분이 어렵다.
**권고**: 트리거 조건에 "1차 데이터(인터뷰, 테스트) vs 2차 데이터(웹, 학술, 커뮤니티)" 구분을 명시하면 충돌 감소.

---

### 충돌 패턴 B: ui-design vs ui-build

| 충돌 쿼리 | ui-design 근거 | ui-build 근거 | 판정 |
|----------|---------------|-------------|------|
| "디자인 토큰 작업해줘" | '디자인 토큰 정의' | '디자인 토큰 구현' | **모호** — '작업'이 정의인지 구현인지 불명확. 충돌 가능성 높음. |
| "디자인 시스템 만들어줘" | '디자인 시스템' 키워드 매칭 | '디자인 시스템 코드' 키워드 매칭 | **모호** — 시스템 '설계'인지 '코드화'인지에 따라 다름. |
| "Figma 보고 컴포넌트 만들어줘" | 'Figma' 키워드 매칭 | 'Figma to Code' 매칭 | **ui-build가 적합** — '만들어줘' = 코드 생성 의도. 그러나 'Figma' 키워드가 ui-design도 트리거할 수 있음. |
| "카드 컴포넌트 설계해줘" | '컴포넌트 명세' 작성 | '카드 컴포넌트' 코드 생성 | **ui-design이 적합** — '설계'가 핵심. 그러나 '카드 컴포넌트'가 ui-build도 트리거할 수 있음. |

**심각도**: 높음. 두 스킬이 "디자인 토큰", "디자인 시스템", "컴포넌트", "Figma" 키워드를 공유한다.
**권고**: 동사(verb)로 구분하는 규칙 추가 — '정의/설계/잡다' = ui-design, '구현/만들기/코드/변환' = ui-build.

---

### 충돌 패턴 C: design-ops vs 개별 스킬

| 충돌 쿼리 | design-ops 근거 | 개별 스킬 근거 | 판정 |
|----------|---------------|-------------|------|
| "사용자 조사하고 와이어프레임도 그려줘" | 2단계 복합 요청 = 오케스트레이션 | ux-research + ui-design 각각 | **design-ops가 적합** — 의도된 충돌. 복합 요청은 오케스트레이터가 받아서 분배. |
| "리서치부터 해줘" | '리서치부터' = 이후 단계 암시 | ux-research 또는 deep-research | **모호** — '부터'가 전체 프로세스를 암시하는지, 리서치만 시작하는 건지 불확실. |
| "UX 리서치를 팀으로 진행해줘" | '팀으로' = 팀 협업 요청 | ux-research 단독 | **design-ops가 적합** — '팀'이 명시되면 오케스트레이터. 그러나 리서치만 필요할 수도 있음. |

**심각도**: 낮음~중간. design-ops의 트리거 조건("여러 단계를 아우르는", "팀", "전체 프로세스")이 개별 스킬과 잘 구분된다. 단, "A하고 B도 해줘" 패턴에서 A, B가 서로 다른 스킬일 때 design-ops vs 순차적 개별 스킬 호출의 경계가 모호하다.
**권고**: "2개 이상의 서로 다른 스킬 영역에 걸치는 요청은 design-ops가 우선한다"는 명시적 규칙 추가.

---

### 충돌 패턴 D: deep-research vs ui-design (벤치마크 영역)

| 충돌 쿼리 | deep-research 근거 | ui-design 근거 | 판정 |
|----------|-------------------|---------------|------|
| "경쟁사 UI를 분석해줘" | '경쟁사 분석' | 'UI' + 분석 | **deep-research가 적합** — 외부 데이터 수집이 핵심. 그러나 'UI 분석'이 ui-design을 트리거할 수 있음. |
| "다른 앱들의 네비게이션 패턴 조사해줘" | '벤치마크', '조사' | '네비게이션 설계' | **deep-research가 적합** — '다른 앱들' = 외부 조사. '네비게이션' 키워드가 ui-design을 부분 매칭. |

**심각도**: 낮음. 대부분의 경우 '조사/분석/벤치마크' 동사가 deep-research를 우선 트리거하므로 실제 충돌은 드물다.

## 7. 종합 권고

### 충돌 심각도 순위

| 순위 | 충돌 쌍 | 심각도 | 핵심 원인 |
|------|--------|--------|----------|
| 1 | ui-design vs ui-build | **높음** | "디자인 토큰", "디자인 시스템", "컴포넌트", "Figma" 키워드 공유 |
| 2 | ux-research vs deep-research | **중간** | "리서치", "조사", "분석" 키워드 공유 |
| 3 | design-ops vs 개별 스킬 | **중간** | 복합 요청의 경계 모호 |
| 4 | deep-research vs ui-design | **낮음** | "벤치마크" 영역에서만 접점 |

### 개선 제안

1. **동사(verb) 기반 분기 규칙 추가**: "정의/설계/잡다" vs "구현/만들기/코드화/변환"으로 ui-design과 ui-build를 명확히 분리.
2. **데이터 소스 기반 분기**: 1차 데이터(자사 사용자) = ux-research, 2차 데이터(외부 소스) = deep-research.
3. **복합 요청 우선 규칙**: 2개 이상의 스킬 영역에 걸치는 요청은 design-ops가 항상 우선.
4. **Figma 컨텍스트 분기**: Figma 파일 "분석/읽기" = ui-design, Figma 파일 "코드 변환" = ui-build.
5. **description에 NOT-trigger 힌트 추가**: 각 스킬의 description에 "이 스킬이 아닌 경우"를 명시하면 LLM의 트리거 정확도가 향상된다.
